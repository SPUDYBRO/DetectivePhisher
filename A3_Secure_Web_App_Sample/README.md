# A3 Secure AI Web Application — Teaching Sample

This sample is deliberately small. It is intended to show students **what Assignment 3 looks like as a complete system**, not to provide a solution to copy.

The key idea is that Assignment 2 and Assignment 3 are separate:

```text
Assignment 2
train / evaluate model
        ↓
export .joblib or .pkl
        ↓
Assignment 3
FastAPI loads trained model
        ↓
React sends user input
        ↓
model calculates result
        ↓
FastAPI returns JSON
        ↓
React + D3.js display result
        ↓
security attack / defence / evidence
```

The sample therefore uses **synthetic randomly generated training data**. The models are intentionally imperfect because:

> **Assignment 3 does not mark model accuracy.**

The focus is the full-stack application, security controls, and convincing demonstration.

# 1. Four topic models

The sample contains four small trained models.

| Topic | ML task | Model | Example output |
|---|---|---|---|
| Phishing URL Detection | Classification | Random Forest | Phishing / Legitimate + probability |
| Prompt Injection Guardrail | Classification | TF-IDF + Logistic Regression | Allow / Block + probability |
| AI-generated Content Detection | Classification | Logistic Regression | AI-generated / Human-made + probability |
| Log Anomaly Detection | **Clustering** | **K-Means** | Normal / Anomalous + anomaly score |

Typical metrics generated by the supplied random seed are approximately:

```text
Phishing classification:     Accuracy ≈ 0.88
Prompt classification:       Accuracy ≈ 0.88
AI-content classification:   Accuracy ≈ 0.82
Log K-Means:                 Silhouette ≈ 0.55
```

These values are intentionally not perfect.

For the clustering example, the model is trained **without class labels**. After clustering, the cluster with the higher-risk centroid is described as `Anomalous` for the application display. This is a useful example of how clustering differs from supervised classification.

# 3. Retrain and export the models

The model files are already included, but for teaching it is useful to show how they were created.

From `backend/`:

```bash
source .venv/bin/activate
python3 train_models.py
```

This runs the four training pipelines and exports the models using:

```python
joblib.dump(bundle, path)
```

The sample also exports a `.pkl` copy of the phishing model to demonstrate the alternative format.

The web application does **not** call `.fit()` again. It loads the trained model:

```python
bundle = joblib.load(path)
```

and performs inference:

```python
model.predict(...)
model.predict_proba(...)
```

The training script also generates:

```text
model_hashes.json
```

which is used by the Unsafe Model Loading defence.

# 4. Topic-specific front-end behaviour

Use the topic selector at the top of the page.

Each topic changes the sample input and returned information.

### Phishing URL Detection

Input:

```text
URL
```

Result includes:

- Phishing / Legitimate
- probability
- URL length
- HTTPS
- IP hostname
- subdomains
- suspicious keyword count
- digit ratio

The backend analyses the URL string only. It does **not** visit the submitted site, so this architecture does not introduce SSRF merely for the sake of the demo.

### Prompt Injection Guardrail

Input:

```text
user message
```

Result includes:

- Allow / Block
- injection probability
- text length
- word count
- visible suspicious terms

### AI-generated Content Detection

Input:

```text
text
```

Result includes simple stylometric features such as:

- average word length
- average sentence length
- lexical diversity
- repeated-word ratio
- sentence-length variation

### Log Anomaly Detection

Input:

```text
log session
```

The K-Means model receives parsed features such as:

- failed logins
- errors
- warnings
- unique IPs
- number of log lines

The displayed anomaly score is a teaching score, **not a calibrated probability**.

# 6. Section 2.7 — Security Defence 1: Missing Rate Limiting

The Security panel can run the complete demonstration automatically.

Click:

```text
Run before / after test
```

The backend simulates 10 requests.

Before defence:

```text
10 / 10 accepted
```

After a limit of 5 requests per 60 seconds:

```text
5 / 10 accepted
5 / 10 rejected
```

The rejected requests correspond to:

```text
HTTP 429 Too Many Requests
```

This is relevant to all four topics because they expose model inference / analysis endpoints that can be called repeatedly.

A real prediction endpoint in the sample also has a simple backend limiter. Front-end button disabling alone would not be sufficient because an attacker can bypass React and call FastAPI directly.

# 7. Section 2.7 — Security Defence 2: Unsafe Model Loading

The backend normally loads models such as:

```text
models/phishing.joblib
```

`pickle` and `joblib` deserialisation should not be performed on an untrusted file.

The sample therefore calculates an approved SHA-256 hash during training and verifies the hash **before** calling `joblib.load()`.

The page contains an automated integrity demonstration.

Click:

```text
Run integrity test
```

The demonstration safely creates a benign replacement `.joblib` file.

Before defence:

```text
replacement model file
        ↓
joblib.load()
        ↓
file is deserialised
```

After defence:

```text
replacement model file
        ↓
calculate SHA-256
        ↓
hash != approved hash
        ↓
reject BEFORE joblib.load()
```

The page displays both hashes as evidence.

Important: the teaching demonstration deliberately uses a **benign** replacement file. It does not create or execute a malicious pickle payload.

# 8. Section 2.8 — Advanced Security

The sample uses **Detection Evasion** against the Prompt Injection model.

Click:

```text
Run advanced experiment
```

The backend sends the **same 30 adversarial inputs** through the model before and after the defence.

Attack examples include:

- Unicode look-alike characters
- zero-width characters
- spacing-based obfuscation

Before defence, some malicious prompts are incorrectly classified as:

```text
ALLOW
```

The defence adds:

```text
Unicode normalisation
+ zero-width removal
+ small homoglyph mapping
```

The same 30 attacks are then run again.

The D3.js chart compares:

```text
Attack success rate before defence
vs
Attack success rate after defence
```

The backend also measures:

- false-positive rate on legitimate inputs
- mean processing latency

This matches the important Section 2.8 rubric logic:

```text
implement attack
        ↓
measure repeatedly
        ↓
baseline
        ↓
implement defence
        ↓
repeat SAME measurement
        ↓
compare attack success
        ↓
measure / explain defence cost
        ↓
interpret honestly
```

A defence does not need to reduce attack success to zero. If some attacks still bypass it, that should be reported honestly.

# 10. Important teaching limitations

This sample intentionally simplifies several things:

- synthetic datasets are used;
- model performance is not production quality;
- the in-memory rate limiter is not suitable for a distributed production deployment;
- the advanced-security homoglyph mapping is deliberately small;
- the explanation fields are descriptive and are not formal model explainability such as SHAP;
- the log anomaly score is not a calibrated probability;
- the sample does not implement authentication, a database, SSRF-prone fetching, or unnecessary architecture solely to manufacture vulnerabilities.

That is intentional. Students should understand the **process** and then make defensible choices for their own application.
